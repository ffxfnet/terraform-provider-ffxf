# terraform-provider-ffxf

Manage FFXF Cloud virtual machines with OpenTofu. Define instance configuration in HCL and let OpenTofu create, update, refresh, and destroy the resources to match your configuration.

The provider supports `ffxf_instance`, `ffxf_vpc`, `ffxf_firewall`, `ffxf_firewall_member`, and the `ffxf_load_balancer`, `ffxf_load_balancer_pool`, and `ffxf_load_balancer_listener` resources. Inventory data sources list firewalls and load balancers with account quotas; `ffxf_load_balancer_metrics` reads request, traffic, connection, and session statistics. Read-only catalog data sources are available for regions, plans, and images.

Use firewalls to manage inbound and outbound rules, then attach them to machines with `ffxf_firewall_member`. Load balancers are attached to a private network and configured with pools (including their complete target sets) and listeners (including their complete routing rules). HTTPS certificates are managed by FFXF Cloud. The instance resource tracks its assigned ID and IPv4 address, and applies hostname changes in place. Changes to plan, region, image, or billing replace the instance; changing a load balancer's VPC also requires replacement.

## Configuration

Provide an FFXF Cloud API token in the provider configuration or set the `FFXF_TOKEN` environment variable. The API endpoint is optional; it defaults to `https://api.ffxf.net/v1`. Set `FFXF_ENDPOINT` to override it through the environment.

```hcl
terraform {
	required_providers {
		ffxf = {
			source = "ffxfnet/ffxf"
		}
	}
}

variable "ffxf_token" {
	type      = string
	sensitive = true
}

provider "ffxf" {
	token = var.ffxf_token
	# endpoint = "https://api.ffxf.net/v1"
}

resource "ffxf_instance" "web" {
	hostname = "web-server-01"
	plan     = "nano"
	region   = "montreal"
	image    = "debian-13"
	billing  = "hourly"
}

data "ffxf_plan" "nano" {
	slug = "nano"
}

data "ffxf_image" "debian" {
	slug = "debian-13"
}

data "ffxf_region" "montreal" {
	slug = "montreal"
}
```

The `billing` argument is optional and defaults to `hourly`. The provider also accepts `FFXF_TOKEN` instead of setting `token` in the provider block. Mark the variable holding your token as sensitive and avoid committing credentials to version control.

## GitHub Actions OIDC

The provider accepts a GitHub Actions OIDC token through `FFXF_TOKEN`, just like an API token. Request the token with the audience generated for your FFXF OIDC provider, then pass it to OpenTofu as `FFXF_TOKEN`. The workflow must grant `id-token: write`.

For this repository, GitHub's subject includes immutable owner and repository IDs. The subject observed for the `main` branch is:

```text
repo:ffxfnet@193109320/terraform-provider-ffxf@1396812060:ref:refs/heads/main
```

Use that exact subject to restrict a binding to `main`, or use `repo:ffxfnet@193109320/terraform-provider-ffxf@1396812060:ref:refs/heads/*` to allow branch refs. The issuer is `https://token.actions.githubusercontent.com`. Configure the audience to match the value generated by FFXF for your OIDC provider.

The OIDC acceptance workflow (`.github/workflows/acceptance.yml`) runs one job per resource area, each with its own configuration in `tests/acceptance/<area>`, so a failure in one area does not hide the others and each can be bound to its own OIDC role. Choose an `area` when dispatching it, or leave it on `all`:

| Area | What it creates and destroys | What it reads |
|---|---|---|
| `vm` | SSH key, VPC, firewall, instance (with `ssh_keys`), firewall and VPC membership, power state, IPv6 address | VM inventory, metrics, backups, actions, network, plans, images, VPCs, SSH keys |
| `account` | none (read-only: account, usage, catalog, and listings of every resource and access object) | account, usage, plan and image catalogs |
| `access` | policy, role, API key, OIDC binding (all new, so the workflow's own access is untouched) | policies, roles, API keys, OIDC providers |
| `loadbalancer` | VPC, instance, VPC membership, load balancer, pool with the VM as target, listener | nothing |
| `database` (beta) | VPC, managed database, fork, user, logical database | database options, credentials, inventory |
| `runners` (beta) | nothing | runners, runner jobs |

`all` runs `vm`, `account`, `access` and `loadbalancer`; set `enable_beta` to add `database` and `runners`, which are billed and need beta access. `ffxf_vm_reinstall`, `ffxf_vm_backup_restore` and `ffxf_account_budget` and `ffxf_database_restore` are not exercised there because they wipe a disk or change account-wide settings. Every resource and data source also has mock-based OpenTofu tests in `tests/terraform`, run with `sh tests/terraform/run.sh`.

Grant only the permissions needed by the configuration. The OIDC binding acts through a role whose policies list `service:action` names; the access-management actions (`policy:*`, `role:*`, `api-key:*`, `oidc-*:*`) only control who can manage keys and bindings and do not authorize any of the calls below. A call outside the policies is refused with `403 insufficient_scope`. Catalog lookups for regions, plans, and images are public.

Ready-to-paste policy documents for each acceptance area are in [`tests/acceptance/policies`](tests/acceptance/policies): `vm.json`, `account.json`, `access.json`, `loadbalancer.json`, `database.json`, `runners.json`, and `all.json` (their union). Create a policy from the document, attach it to a role, and select that role on the binding. `ffxf_account_budget` additionally needs `billing:update`, `ffxf_vm_rdns` needs `vm.rdns:update` (and a hostname that already resolves to the address), `ffxf_vm_reinstall` needs `vm:action`, and `ffxf_vm_backup_restore` needs `vm.backup:restore`. The documents write `vm.ipv*:create` instead of `vm.ipv6:create` because the console's action-name check does not accept digits.

## Access management

`ffxf_policy`, `ffxf_role`, `ffxf_api_key` and `ffxf_oidc_binding` manage who may call the API, and `ffxf_policies`, `ffxf_roles`, `ffxf_api_keys` and `ffxf_oidc_providers` read them. Caveats:

- Writes are refused for temporary (`ffxf_at_`) tokens; authenticate with an API key or a direct OIDC token.
- A credential cannot modify a role or policy it holds or can assume, nor its own binding.
- A role still used by a key or binding cannot be deleted or emptied, and a policy attached to a role cannot be deleted.
- `ffxf_api_key` has no update: any change replaces it. Its secret `token` is only returned at creation and is stored (sensitive) in state; it is empty after an import.
- OIDC providers are read-only. A binding must include a `sub` claim condition naming its owner.
